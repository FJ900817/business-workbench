# Agent Note: Local macOS Voice Companion

Status: implemented

English | [中文](2026-08-22-local-macos-voice-companion.zh.md)

## Problem

The local macOS wrapper presents Harness as a desktop application, but conversation still requires returning to the main window and typing. A desktop voice companion must stay reachable above other applications without creating a second model configuration, bypassing the current session's permissions, or moving tool execution outside Harness.

## Decision

The native wrapper owns a transparent floating `NSPanel` with compact and expanded forms. The panel joins every Space, stays above ordinary windows, supports dragging, and remains alive when the main Harness window closes. A voice turn opens the compact form; expansion remains an explicit double-click action. Its deep-blue asymmetric shell continuously rotates, stretches, and changes outline even while idle; brighter electric-blue filaments, flowing particles, a luminous core, and microphone amplitude distinguish listening, thinking, tool execution, speaking, and failure states. The Web view provides a waveform plus **Voice** label beside **Settings** and a black circular waveform in an empty composer. The bridge treats the native send button's enabled state as authoritative and also observes text input, paste, drop, and attachment elements, so text or a file immediately replaces that composer control with the black send arrow. A document-level pointer-down handler owns the visible composer-control bounds, preventing the underlying disabled primary button from swallowing the voice action.

The wrapper uses the macOS Speech framework for live Chinese transcription. The bridge emits completed short clauses while the assistant is still streaming. Native playback begins on the first clause, pre-generates the next clause during playback, and resumes listening after the response. During playback, the wrapper feeds a voice-processed microphone tap to both a foreground-energy detector and a partial Chinese recognition task. Sustained energy or a recognized phrase that is not contained in the current spoken clause becomes a barge-in: playback stops, the bridge activates the visible Harness stop control, and normal recognition begins while retaining the recognized interruption phrase. The wrapper waits for the composer to leave its busy state and retries the retained utterance for a bounded period before reporting failure. A click provides the same deterministic interruption path during speaking, thinking, or tool execution. The answer row remains hidden during the spoken turn and is revealed after playback. DOM extraction excludes reasoning, code, controls, and non-prose elements before local cleanup removes presentation syntax, non-verbal Unicode, English-only stream fragments, and every leading non-Chinese block when Chinese prose follows. Speech cleanup rewrites common report transitions into short spoken Mandarin, uses smaller clauses, and caps one spoken turn while preserving the complete written response.

Online natural speech is opt-in. When permitted, a pinned `edge-tts` runtime with `zh-CN-YunxiNeural` receives one short clause at a time and is preferred for lower first-clause latency and informal Mandarin prosody. The native choice states that selected answer clauses go to the Microsoft Edge speech service while credentials, files, and the complete conversation remain excluded. Rejecting online output selects the isolated Python 3.12 Kokoro 82M runtime with its Mandarin `zm_yunxi` voice. Its app-owned daemon loads once, accepts bounded requests through a mode-0600 Unix socket, and exits when its owning desktop PID disappears. A selected neural backend failure ends the spoken turn and resumes listening; it never changes voice by falling through to `AVSpeechSynthesizer`. One persistent AVAudioEngine graph applies slight pitch, equalization, delay, and reverb without rebuilding the output device. Microphone, Speech Recognition, and Documents-folder purposes are declared in the application property list.

A main-frame `WKUserScript` adds the two application-only entry points and exposes one private bridge to the native wrapper. A recognized utterance is written into the active conversation textarea through its native value setter and ordinary input events, then the existing primary action submits it. This keeps the active session's selected model, workspace, permission preset, skills, credentials, and tools authoritative. The bridge tracks only the turn it submitted, maps visible streaming and tool rows to orb states, and sends incremental clauses to native speech synthesis.

The native menu provides show/hide and start-listening commands. Separate mouse-down, drag, and mouse-up handling keeps a single click available for interruption while a double click changes size and a drag moves the panel; the right-click menu exposes the same actions. The main window opts out of release-on-close so a Dock reopen retains a valid window object. Closing that window does not terminate the owned Web server; quitting the application still stops recognition, speech, and the server.

The wrapper starts the owned Web server and updater subprocesses with an explicit command search path containing both Intel and Apple Silicon Homebrew locations. Profile-installed Web plugins can therefore resolve `pnpm`, `corepack`, or `npx` when the application starts from Finder, whose inherited path otherwise contains only system directories.

The voice companion does not receive general screen contents, browser media, or unrestricted computer control. Page reading and host actions continue to use Harness tools and their existing permission flow; a future native context provider must enter through an explicit Harness capability rather than scraping or executing outside the session log.

The configured DeepSeek and Kimi providers remain text-turn models. Streaming clause playback, automatic listening, and barge-in improve conversational turn-taking but do not create an audio-native full-duplex model session. Simultaneous semantic audio input and output requires a provider capability with a real-time audio protocol.

## Verification

The Swift wrapper compiles for arm64 macOS 13 with AppKit, WebKit, AVFoundation, and Speech. A standalone Swift regression executable covers removal of emoji, URLs, long English/code prefixes, code, English-only stream fragments, conversational transition rewriting, playback-echo classification, and segment generation. The injected bridge passes JavaScript syntax checking. Installed-application checks cover the sidebar entry, the composer voice action, compact startup, typed-draft send control, main-window-independent animation, Dock reopen, loopback server ownership, and bundle signature. On the measured Apple M4 host, the warmed installed daemon generated a 2.9-second WAV in 1.8 seconds and retained about 750 MB RSS. Barge-in threshold quality, subjective audio quality, and a real provider response still require user listening and are not covered by the repository's keyless snapshot harness.

## Alternatives considered

- **Browser-only speech APIs and a DOM overlay**: this cannot keep the companion above other applications after the main window closes and gives inconsistent microphone behavior across WebKit versions. Native macOS frameworks own the system-level interaction.
- **A separate voice model and conversation service**: this duplicates credentials and can disagree with the model, workspace, and permission state visible in Harness. Submitting through the active composer keeps one session authoritative.
- **Directly invoking Harness internals from injected JavaScript**: private runtime objects would couple the wrapper to browser implementation details. The bridge uses the user-visible composer and conversation attributes already rendered by the application-only Web view.
- **Immediate unrestricted screen and computer access**: this would bypass Harness tool approvals and model-visible logging. The first implementation leaves those actions to existing Harness capabilities.

## Consequences

The installed application provides a movable, resizable, automatically continuing voice interaction surface without a terminal or a second model setup. Recognition depends on macOS Speech availability. Local natural output adds approximately 1.3 GB of installed files and about 750 MB of warmed-process memory on the measured Apple M4 host. Online natural output depends on its pinned Python runtime and network service after explicit consent. A selected neural backend failure ends that spoken turn instead of switching voices. The user must grant Documents, Microphone, and Speech Recognition permissions when macOS first asks.

The DOM bridge is local to the native wrapper and must track material changes to the conversation composer or chat attributes, including the stop control used to cancel an active turn. Neural output is ordinary speech synthesis, not voice cloning, and does not fall through to a different system voice on failure. Host-wide page capture and computer operation remain outside this feature until Harness supplies explicit logged capabilities for them.
